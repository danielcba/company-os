# Request for Comments (RFC)

Version: 1.0
Status: Official
Owner: Company OS

---

## Purpose

The RFC process is the formal mechanism for proposing changes to Company OS.

RFCs allow the project to evolve through deliberation, not impulse.

Every significant change — architectural, conceptual, or procedural — must pass through this process.

---

## When an RFC Is Required

An RFC is required when a proposal:

- Adds, modifies, or removes a Core Concept,
- Modifies a Cognitive Principle,
- Changes a relationship type,
- Alters the Cognitive Flow,
- Changes the repository structure,
- Changes any Official document,
- Introduces a new architectural component.

Minor edits, corrections, and clarifications do not require an RFC.

---

## RFC Lifecycle

1. **Draft** — the proposal is written and submitted.
2. **Review** — the proposal is discussed, refined, and evaluated against the Cognitive Principles and Design Rules.
3. **Accepted** — the proposal is approved and merged.
4. **Rejected** — the proposal is declined, with recorded reasons.
5. **Superseded** — the proposal is replaced by a newer RFC.

---

## RFC Template

Every RFC must include:

- Title
- Number
- Status
- Author
- Date
- Motivation — why this change is needed
- Proposal — what changes
- Consequences — what this change affects
- Alternatives considered
- Evaluation against the Design Rules

---

## RFC Numbering

RFCs are numbered sequentially: `RFC-0001`, `RFC-0002`, ...

---

## Principles of the RFC Process

- The ontology evolves through discovery, not assumption.
- A proposal is only as strong as its evaluation against the Principles.
- The repository is the single source of truth.
- The architecture should guide the code, never the opposite.
